# whisper-si: a Whisper-tiny ASR accelerator as a Chisel generator

Technical report, 2026-09-08. Repository `tibrewalrachit/wispr-on-chip`, branch
`claude/whisper-tiny-chisel-accelerator-03do1o`, commit `912af28`.

## 1. Summary

whisper-si is a from-scratch hardware implementation of OpenAI's Whisper-tiny speech recogniser
(37.18 M parameters, 4 encoder and 4 decoder layers, d = 384, 6 heads) written as a Chisel generator.
The whole model runs on one chip: a 32×32 int8 weight-stationary matmul engine, a 16-lane vector unit
for LayerNorm, quantisation and residual adds, an attention unit with online softmax, a KV cache, a
streaming argmax sampler, and a sequencer that executes a 186-instruction micro-program generated
from the model graph. All 247 weight tensors (86.6 MB of hex text) are committed to the repository and
consumed at elaboration time through one of three interchangeable weight-store backends.

Correctness is defined by an integer golden model in numpy (`golden/whisper_int.py`): the RTL is
correct if and only if it produces the same bits. That property holds at every level tested.

| Level | What was compared | Result |
|---|---|---|
| Ops | every fixed-point op vs float | 18 pytest cases pass |
| Golden model vs fp32 Whisper | WER on 200 LibriSpeech test-clean utterances | 5.52 % int vs 5.54 % fp32 (gate: ≤ fp32 + 0.5) |
| Matmul engine | 19 vector cases incl. every real weight shape | bit-exact, 99.7 % MAC utilisation at M = 1500 |
| Weight backends | RomLiteral, RomInit, Sram on real tensors | identical data at every address, 13/13 |
| Vector unit, attention, KV path | 14 cases from golden dumps | bit-exact |
| Full chip on Verilator | 35 full-context runs (24 distinct clips) | tokens identical to golden on 35/35 |
| RTL word error rate | 20 test-clean utterances | 7.58 % vs fp32 8.08 % (gate: ≤ 8.58 %) |

A 30 s window costs 42.1 M cycles plus about 200 k cycles per generated token. An analytic cycle
model built only from unit-level measurements predicts every measured end-to-end run within 0.2 %.

## 2. Method: the golden model is the specification

The project was run in five phases, each ending with a commit and a status entry
(`docs/status.md`), and every design choice that deviates from the brief is a dated, numbered entry
in `docs/decisions.md`.

The central rule is that numerics are frozen in Python before any RTL exists. `golden/whisper_int.py`
is a complete integer implementation of Whisper-tiny: it takes an int8 log-mel spectrogram and
produces token ids using only integer multiplies, shifts, saturations and lookup tables. The only
floating-point code is in `golden/quant.py`, which turns the fp16 checkpoint plus calibration
statistics into int8 weights, int32 multipliers and shift amounts. Because the golden model is
executable, it doubles as the vector generator: every RTL unit test loads tensors dumped by it, and
the end-to-end test compares the RTL's token stream with the golden token stream, not with the
floating-point model.

Accuracy is checked separately, once, at the golden level. The fp32 reference is openai-whisper's
own greedy decoder over a single 30 s window (`golden/reference_cpu.py`), regenerated byte-identically
and cross-checked against the HuggingFace weights (zero difference on 60 clips). The gate is that the
integer model's WER may exceed fp32 by at most 0.5 points absolute on the 200-utterance set. It
passes with margin: 5.52 % versus 5.54 %.

## 3. Numerics

The datapath is W8A8 with an int16 residual stream. `docs/numerics.md` is the normative text; the
essentials are:

* **Weights** are int8, symmetric, per output channel. **Matmul inputs** are int8 with a per-token
  dynamic scale: for each row the vector unit finds `maxabs`, computes a reciprocal
  `recip = floor((127·2^16 + maxabs/2) / maxabs)` and quantises `a8 = sat8(rsr(x16·recip, 16))`.
  The row's `maxabs` travels with the tile as a "rowfac" so the matmul edge can undo it.
* **Matmul edge requantisation** is fused into the engine's drain: `t = sat40(rsr(acc·M[n], s1))`,
  `y = satW(rsr(t·rowfac[m] + (B[n] << (s2−16)), s2))` with s2 = 24 for int8 outputs and 20 for
  int16. A "wide" mode for the LM head keeps int32 logits for the argmax.
* **The residual stream is int16** (decision #5). Calibration on 128 dev-clean utterances showed
  encoder residual maxima of 274 against channel medians of 5.8; an int8 residual leaves typical
  values 0–2 LSBs and gives 98 % WER. Int16 is a config parameter; int8 remains selectable.
* **LayerNorm** uses an integer mean (`sum·5592405 >> 23`), a variance from the Σx/Σx² identity, a
  256-entry inverse-square-root table with one Newton step, and per-channel gain and bias folded
  into the output scale. **GELU** is `x·Φ(x)` with a 256-entry Φ table and linear interpolation on
  the int16 fc1 output (decision #6); an int8→int8 GELU table costs 21 % WER.
* **Attention** uses static per-head Q and K scales and a per-tensor V scale, because per-token
  scales cannot be factored out of the softmax. Scores are processed in key tiles of 64 with an
  online softmax: a running maximum, a Q1.15 exponential table with interpolation, an alpha
  rescale when the maximum grows, and a 36-bit accumulator for P·V. The final division uses a
  reciprocal `floor((2^40 + l/2)/l)` from a pipelined divider.
* **Decoding** replicates Whisper's greedy rules exactly: a four-token prompt, sampling from position
  3, suppression of 88 non-speech tokens (plus blank and end-of-text on the first step), lowest-index
  argmax, stop at end-of-text or after 224 tokens.

Every rounding is `rsr(x, s) = (x + 2^(s−1)) >> s`; every saturation is explicit. There is no
tolerance anywhere: hardware and Python must agree to the bit.

## 4. Weights in the source tree

`gen/dump_weights.py` writes each tensor as a hex file under `weights/`, one 32-bit little-endian
word per line, plus `MANIFEST.json` with shape, kind, scales, word count and sha256. Three kinds
exist: `w8` matmul tiles, `i32vec` parameter vectors (multipliers, biases, LayerNorm gains) and
`i8mat` byte matrices (positional embeddings). The tile layout (`docs/tiling.md`) makes one memory
word equal one 8-row group of a 32×32 tile, 2048 bits, so a tile loads in four cycles.

At elaboration `WeightTensor` re-hashes each file against the manifest and exposes it to the
`WeightStore`, which has three backends behind one read-port interface:

| Backend | Mechanism | Use |
|---|---|---|
| RomInit | `SyncReadMem` initialised by `$readmemh` from an image derived at elaboration | full-chip simulation (default) |
| RomLiteral | `VecInit` of literals, a true synthesisable ROM | ASIC flow; proven on three real tensors up to 4.7 Mbit |
| Sram | `SyncReadMem` with a load port | FPGA or off-chip weights |

`WeightStoreEquivalenceSpec` reads every address of real tensors of all three kinds through each
backend and checks identical data. The full model as literals would need about three hours of
Verilator build, so RomInit is the simulation default and the literal path is proven on encoder
layer 0's six tensors (decision, Phase 5).

## 5. Architecture

### 5.1 Top level

`WhisperTop` exposes a register bus, a mel input stream, a token output stream with a 256-deep
queue, and a debug read port into the activation banks. The host writes the language token and
frame count, streams int8 mel rows, and sets a start bit; tokens appear on the output stream and a
done flag rises when the sequencer halts. Breakpoint and resume registers pause the sequencer at any
micro-instruction so a test can inspect on-chip memories.

Inside are eight activation banks (256-bit logical words, 512-bit physical, totalling 230 k words),
side tables of per-row scale factors, the weight store, and five execution units driven by the
sequencer through irrevocable Decoupled command handshakes.

### 5.2 Matmul engine

The engine is a 32×32 array of int8 multiply-accumulate cells, weight-stationary and output-tiled:
for each output column tile it walks the reduction tiles, loads a 32×32 weight tile in four cycles
from the 2048-bit ROM word, then streams all M rows of activations through it, accumulating into a
1536-row × 32-column int32 accumulator. The array is organised as four pipeline stages of eight
combinational MAC rows (decision #9): a fully skewed systolic array would need either a 2048-bit
32-stage load chain or a 32-cycle tile switch, whereas eight rows per stage matches the ROM word to
one stage and keeps a five-cycle latency. Activations broadcast along rows and partial sums flow
down; a reset-initialised valid chain guarantees no spurious output beats.

The drain path performs the fused requantisation above and routes each 32-wide output row to one of
four sinks: an activation bank, the attention unit, the sampler, or the KV cache. Per-job cost is
`KT·NT·(M+4)+10` cycles, which gives 99.7 % utilisation on a 1500×384×384 job and five cycles per
tile at M = 1, the decoder case, where the design is weight-port bound by construction (decision #8:
a 32-byte port would give 1/32 utilisation and about 1 M cycles per token).

### 5.3 Vector unit

A 16-lane unit executes LayerNorm, dynamic quantisation, scaled adds and embedding extraction on
one row at a time in three passes over a 384- or 1536-wide row. Each op may fuse a GELU on its
input and optionally consumes a second operand from a bank or a parameter ROM. Measured costs per
row: LayerNorm 123 cycles, dynamic quant 85, fused GELU + quant over 1536 columns 229, scaled add
30–33. The row-oriented design is what allows the encoder to run every op on 1500 rows without
storing anything wider than one row in registers.

### 5.4 Attention and KV cache

The attention unit does not own a multiplier array: it drives the matmul engine. For each head and
each 64-query block it issues, per 64-key tile, one S = Q·Kᵀ job (K is read straight from the KV
cache as the stationary tile), runs the online softmax over the 64 scores of each query in 12 cycles,
then issues two P·V jobs (the 16-bit probabilities are split into unsigned high and low bytes so the
int8 array can be reused; the results are recombined exactly). After the last key tile a pipelined
41-bit divider finalises each query row in 31 cycles. Masks handle ragged tiles and causality.

The KV cache stores K transposed (one word = 8 head-dims × 32 keys) and V key-major (8 keys × 32
dims) so both feed the engine's weight port directly. A double-buffered transposer accepts the
engine's output rows without stalling, and byte-masked writes append single keys during decoding.
Regions exist for encoder self-attention, decoder self-attention (448 positions) and the cross
attention K/V computed once after the encoder.

### 5.5 Sequencer and micro-program

The model graph is not hard-wired. `gen/emit_microcode.py` walks the layer structure and emits 186
instructions into `generated/Microcode.scala` (listing in `docs/microcode.txt`); each instruction
carries a complete command bundle for one unit plus runtime selectors: rows may be a constant, the
frame count, the context length or the current chunk; bases may be offset by the chunk or the
decoder position; key counts may be the context length or `pos + 1`. Control opcodes implement
chunk loops (conv1 in 1536-row chunks, FFN in 512-row chunks to fit the hidden bank), the prompt
branch, position increment and halt. The encoder therefore runs for any `n_frames ≤ 3000` and the
decoder loop is 92 instructions executed once per position.

### 5.6 Sampler

The LM head is a wide-mode matmul over the 51872-column padded vocabulary that streams its int32
logits into the sampler, which keeps a running lowest-index maximum, applies the suppression mask
ROM and the first-step blank rule, emits the token, and either loops the sequencer or halts.

## 6. Verification

### 6.1 The ladder

1. `golden/tests`: each fixed-point op against float, tile-order invariance of the matmul,
   masked-key independence of attention, im2col against torch's conv.
2. Vector generators dump real activations from the golden model on a 2 s clip:
   `MatmulEngineSpec` (10 random shapes plus every real weight shape from conv1 to the LM head),
   `VectorUnitSpec` (9 cases), `AttentionSpec` (a full 128×128 encoder layer, a ragged 100×70 case,
   decoder self and cross attention at position 41), `KVWriteSpec` (engine-to-cache path).
3. `RomLiteralLayerSpec` re-runs the real-tensor engine cases with literal ROMs.
4. `E2ESpec` runs whole clips; `E2EDebugSpec` pauses at chosen micro-instructions, dumps the banks
   and `tests/e2e/compare_dumps.py` diffs them against golden dumps of the same tensors.

All Verilator runs carry assertions: engine sinks never stall, every command handshake is
irrevocable, rows and tiles are in range, cache and bank addresses are in range with no same-bank
port conflicts, and emitted token ids are below 51865. A requant saturation counter is exposed as a
register.

### 6.2 End-to-end results

Every clip is run at the full 3000-frame window (decision #12: Whisper-tiny repeats itself when the
encoder context is shorter than it was trained on; with a 5 s pad the WER on short clips is 179 %,
and the fp32 model behaves the same). Runs took 54 min per clip locally and were parallelised one
container per clip on Modal with the same image and the committed weights.

| Set | Clips | Tokens identical to golden | RTL WER | fp32 WER |
|---|---|---|---|---|
| smoke: 2 s clip at 1024 and 3000 frames | 1 | 2/2 runs | 0 % | 0 % |
| default: 2/5/12 s clips + 10 short test-clean utterances | 13 | 13/13 | 12.75 % on the 10 utterances | 12.75 % |
| long: 20 test-clean utterances + 29 s clip | 21 | 21/21 | 7.58 % on the 20 utterances | 8.08 % |

The 29 s clip generates 89 tokens over 60 M cycles and matches token for token. Where the RTL text
differs from the fp32 text ("Hello Bertie" versus "Hey Bertie", "clasped" versus "clashed") the
golden integer model differs in exactly the same way, so the difference is quantisation, not
hardware. The per-clip tables with cycle counts and wall time are in `docs/status.md`.

### 6.3 Bugs the ladder caught

Unit level: a pipelined divider produced one extra quotient bit (attention outputs exactly 2×), a
half-word misalignment in the vector unit's third pass, a valid-chain reset skew that produced
spurious engine beats, a 16-bit overflow of the softmax alpha. Chip level, found by breakpoint
bisection: the GELU fused into the conv2 add was never applied; the KV transposer stalled the
engine; firtool silently dropped byte masks on a memory that had one unmasked port (decision #13,
now a rule: every port of a masked memory carries a data-dependent mask); the KV key index used the
scale-factor row instead of the tensor row. Each fix is covered by a unit test that fails without it.

## 7. Performance

### 7.1 Cycle model

`tests/e2e/cycle_model.py` sums, over the micro-program, the engine formula `KT·NT·(M+4)+10`, the
per-row vector-unit costs and an attention formula (`1+4(rows+4)+13` for each engine job, 12 cycles
per query row of softmax, 31 per query row of finalisation), all measured at unit level in Phases 2
and 3. Nothing was fitted to end-to-end runs.

| Clip | Frames | Tokens | Measured cycles | Model | Ratio |
|---|---|---|---|---|---|
| 2 s | 1024 | 6 | 10,153,984 | 10,176,473 | 1.002 |
| 2 s | 3000 | 6 | 42,135,552 | 42,175,157 | 1.001 |
| 3.6 s utterance | 3000 | 12 | 43,401,216 | 43,444,109 | 1.001 |
| 12 s | 3000 | 55 | 52,477,952 | 52,538,265 | 1.001 |
| 29 s | 3000 | 89 | 59,731,968 | 59,808,337 | 1.001 |

Cycle counts are deterministic: the same clip gives the same count locally and in the cloud.

### 7.2 Where the cycles go

At 3000 frames with 6 generated tokens: encoder layers 37.2 M (88 %), of which attention is 23.1 M,
or 55 % of the whole run; conv1 and conv2 1.2 M; final LayerNorm and cross K/V 1.9 M; decoder 1.8 M.
Each generated token costs about 200 k cycles, of which the LM head is 97 k. Over a whole run the
engine is busy 70 % of cycles (measured with the cumulative busy counter at 1024 frames); the
remainder is softmax and vector-unit phases during which the engine idles.

Encoder attention dominates because 1500 queries × 1500 keys × 6 heads × 4 layers pass through one
32-column array and one 16-lane softmax. The obvious next steps are a second softmax pipeline
overlapping the P·V of one tile with the exponentials of the next, and running the vector unit
concurrently with the engine on independent rows; the analytic model makes both easy to size. At a
nominal 500 MHz the current design transcribes a 30 s window in about 85 ms plus 0.4 ms per token,
and section 7.4 reports the synthesis that supports (and qualifies) that clock figure.

### 7.3 Simulation cost

Elaboration with firtool takes 16 s including the 247 `$readmemh` images; Verilator verilates in
8 s and compiles in about 160 s. Throughput is 12–13 k cycles/s on four threads locally and
6.6–8.9 k cycles/s on Modal's 8-vCPU containers, so a full-context clip is 54 minutes locally and up
to 2.5 hours in the cloud. The harness keeps the RTL honest: tokens accumulate in the on-chip queue
and the host polls the done flag every 4096 cycles, so no compute is skipped (decision #14).

### 7.4 ASAP7 7 nm synthesis

Every compute block was synthesised with Yosys and ABC onto the ASAP7 predictive PDK (7.5-track
RVT cells, typical corner) against a 1 ns target, memories black-boxed. Logic totals 0.28 mm².

| Block | Area (mm²) | Critical path (ps) |
|---|---|---|
| Matmul engine (array + requant + control) | 0.120 | 1267 |
| Attention (softmax, divider) | 0.059 | 5824 |
| Vector unit (16 lanes) | 0.050 | 4843 |
| Weight store mux (247 banks) | 0.040 | 1027 |
| KV cache logic | 0.010 | 725 |
| Sampler / sequencer | 0.002 | 977 / 981 |

The sequencer, sampler, KV cache and weight-store mux meet 1 GHz. The attention unit and vector
unit do not: both put a whole arithmetic chain in one cycle of a step-sequenced state machine, the
online-softmax step and the LayerNorm Newton step. Both pipeline mechanically, and the cycle model
prices the softmax pipeline at 8 % more cycles. The array itself is 1.21 ns with 8 MAC rows per
stage and 1.10 ns with 4, so about half its path is the multiplier and accumulate rather than the
chain. Memories dominate area: 119 Mbit of SRAM and 308 Mbit of weight ROM come to roughly
10–13 mm² against 0.28 mm² of logic.

At 1 GHz the measured cycle counts give 42 ms per 30 s window plus 0.2 ms per generated token; as
synthesised (0.17 GHz) the same window is 248 ms.

## 8. Deviations from the brief and known limitations

1. Accuracy runs use the full 30 s window rather than a speech-length context (decision #12). The
   hardware still supports any `n_frames ≤ 3000`; only the WER gate is run at 3000.
2. Int16 residual instead of int8 (decision #5); Φ-table GELU instead of an int8 output table
   (decision #6). Both alternatives are implemented and their WER recorded.
3. Eight MAC rows per pipeline stage instead of a fully skewed systolic array (decision #9).
4. Whole-model RomLiteral elaboration was not attempted; the literal path is proven per tensor.
5. The checkpoint has 37.18 M parameters, not the 37.8 M quoted in the brief.
6. Calibration used dev-clean only. The noisy and non-English varied clips were transcribed correctly
   by the golden model, but the saturation counter is the only runtime guard.
7. The two e2e sets overlap in 10 utterances, so 24 distinct clips ran on the RTL, not 35.
8. No synthesis or timing has been run; the design targets a single clock with registered memory
   reads and 40-bit accumulators but has only been simulated. SmoothQuant folding exists in the golden
   model but is unvalidated and off.

## 9. Reproducing

```
make setup            # uv env, data cache, checkpoint
make refs-check       # fp32 references are byte-identical
make weights-check    # hex files match MANIFEST.json (sha256)
make golden           # int golden WER on the eval sets
make test             # pytest + six Verilator suites (18 min)
make e2e-smoke        # one 2 s clip on the full chip (~55 min)
make e2e-modal        # default + long sets, one container per clip
make report           # per-clip tables + cycle model
```
